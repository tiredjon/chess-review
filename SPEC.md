## 1. Цель продукта

Веб-приложение для разбора шахматных партий, аналог Chess.com Game Review, но с open-source движком и честными объяснениями:
- точность игрока за партию и по фазам;
- классификация каждого хода (brilliant → blunder);
- объяснение ошибок и тактик человеческим языком, **заземлённое на анализ движка** (без галлюцинаций);
- импорт партий с Lichess / Chess.com / PGN;
- статистика по многим партиям и пазлы из собственных ошибок.

Языки интерфейса и объяснений: RU / EN (UZ — опционально позже).

### Модули backend (`backend/app/`)
- `api/` — роуты: `games`, `analysis`, `imports`, `stats`, `puzzles`, `auth`.
- `core/` — config (pydantic-settings), логирование, DI.
- `db/` — модели, сессии, миграции.
- `engine/` — пул Stockfish-процессов (`EnginePool`), анализ позиции, кэш по FEN.
- `review/` — **чистая доменная логика без I/O**:
  - `winprob.py` — cp/mate → win%;
  - `accuracy.py` — точность хода и партии;
  - `classify.py` — классификация ходов;
  - `phases.py` — дебют / миттельшпиль / эндшпиль;
  - `openings.py` — определение дебюта (ECO), «книжные» ходы;
  - `motifs/` — детекторы тактических мотивов;
  - `pipeline.py` — оркестрация анализа партии.
- `explain/` — построение фактов для LLM, промпты, провайдеры, кэш.
- `importers/` — Lichess API, Chess.com public API, PGN.
- `workers/` — ARQ-задачи.

### Ключевой принцип
Вся логика в `review/` и `explain/facts.py` — детерминированная и покрыта юнит-тестами на фиксированных FEN/PGN. LLM получает **только проверенные факты** и переводит их в текст. LLM не оценивает позиции и не придумывает варианты.

## 4. Доменная логика (точные формулы)

### 4.1 Оценка движка
- Анализ каждой позиции: `depth=18` (настраиваемо), `MultiPV=3`, `Threads` и `Hash` из конфига.
- Оценка всегда нормализуется к точке зрения **игрока, делающего ход**.
- Мат: `mate in N` → cp = ±(10000 − N·10) для win%, но в UI показывать `#N`.
- Кэш: таблица `position_evals` (ключ: FEN без счётчиков ходов + depth + multipv).

### 4.2 Win% (формула Lichess)
```
win% = 50 + 50 * (2 / (1 + exp(-0.00368208 * cp)) - 1)
```
cp обрезать до [-1000, 1000].

### 4.3 Точность хода
```
Δ = max(0, win%_before - win%_after)      # с точки зрения ходящего
acc = 103.1668 * exp(-0.04354 * Δ) - 3.1669
acc = clamp(acc, 0, 100)
```

### 4.4 Точность партии (как у Lichess)
- Окно волатильности: размер = clamp(len(moves)/10, 2, 8).
- Вес хода = stdev(win%) в окне, clamp к [0.5, 12].
- `game_acc = (weighted_mean(acc, weights) + harmonic_mean(acc)) / 2`.
- Отдельно считать точность по фазам.

### 4.5 Классификация ходов
Порядок проверок важен (первое совпадение):

| Класс | Условие |
|---|---|
| `book` | позиция после хода есть в книге дебютов и ход ≤ 15-го |
| `forced` | единственный легальный ход |
| `brilliant` | ход = best или Δ ≤ 2, **и** является жертвой (см. ниже), **и** позиция после хода не хуже −1.0 для ходящего, **и** до хода игрок не был уже в подавляющем выигрыше (win% < 97) |
| `great` | ход = best, и второй вариант MultiPV хуже на ≥ 10 win% (единственный ход), или ход меняет результат (проигрыш → ничья, ничья → выигрыш) |
| `best` | совпадает с PV1 |
| `excellent` | Δ ≤ 2 |
| `good` | Δ ≤ 5 |
| `inaccuracy` | Δ ≤ 10 |
| `mistake` | Δ ≤ 20 |
| `blunder` | Δ > 20 |
| `miss` | дополнительный флаг: соперник ошибся (prev move mistake/blunder), а игрок не наказал (Δ ≥ 10 относительно лучшей линии) |

**Жертва**: после хода SEE (static exchange evaluation) на отданной фигуре отрицательный, или фигура остаётся под боем без адекватной защиты, и в PV1 материал временно падает минимум на 2 пешки, но оценка держится. Пешечные жертвы `brilliant` не дают.

Все пороги вынести в конфиг `review/thresholds.py`.

### 4.6 Фазы
- Дебют: до выхода из книги или до 12-го хода, что раньше, пока не разменяны ферзи.
- Эндшпиль: суммарный материал без пешек ≤ 13 (Ф=9, Л=5, С/К=3) или ферзей нет и лёгких/тяжёлых фигур ≤ 6.
- Иначе миттельшпиль.

### 4.7 Дебюты
- Встроить TSV-базу дебютов Lichess (`lichess-org/chess-openings`, CC0): ECO, название, EPD.
- Определение дебюта: самое глубокое совпадение по EPD.

## 5. Тактические мотивы (`review/motifs/`)

Каждый детектор — чистая функция `detect(board_before, move, pv) -> list[Motif]`, где `Motif {type, squares, pieces, gain_cp, line}`.

Обязательные (MVP):
1. **hanging_piece** — фигура без защиты под боем / зевок фигуры.
2. **fork** — одна фигура атакует ≥ 2 ценных цели (с учётом шаха).
3. **pin** — абсолютная / относительная связка.
4. **skewer** — линейный удар.
5. **discovered_attack** / discovered check.
6. **double_check**.
7. **mate_threat / mate_in_n** — из оценки движка + PV.
8. **back_rank** — мат / угроза по последней горизонтали.
9. **trapped_piece** — у фигуры нет безопасных полей.
10. **removing_defender** / overload.
11. **promotion** — продвижение / угроза превращения.

Детекторы применяются: (а) к ходу игрока, (б) к лучшей линии PV1 (что упущено), (в) к ответу соперника в PV после ошибки (чем наказывается).

Для каждого детектора — ≥ 3 тестовых FEN (положительные) и ≥ 2 отрицательных.

## 6. Объяснения (`explain/`)

### 6.1 Факты
`facts.py` строит JSON на каждый ход с классом ≥ inaccuracy, а также для brilliant/great/miss:
```json
{
  "move_san": "Nf3", "class": "blunder", "eval_before": "+0.8", "eval_after": "-3.2",
  "best_move_san": "Bxf7+", "best_line_san": ["Bxf7+", "Kxf7", "Ng5+"],
  "refutation_line_san": ["Qb6", "..."],
  "motifs_in_refutation": [{"type": "fork", "piece": "N", "square": "e7", "targets": ["Kg8","Rc8"]}],
  "motifs_missed": [...], "material_swing": "-5", "phase": "middlegame"
}
```

### 6.2 LLM
- Интерфейс `LLMProvider.generate(system, user, max_tokens) -> str`, реализации Gemini/OpenAI/Anthropic, выбор через env.
- Системный промпт: «Ты шахматный тренер. Объясняй **только** на основе фактов. Не придумывай ходы и варианты. 2–4 предложения. Уровень — клубный игрок. Язык: {lang}.»
- Валидация вывода: все SAN-ходы в ответе должны присутствовать в фактах; иначе ретрай 1 раз, затем шаблонное объяснение (fallback без LLM).
- Шаблонные объяснения (`templates.py`) на каждый мотив — работают без LLM вообще.
- Кэш по хешу фактов + язык. Генерация **ленивая**: по клику / при открытии ревью, батчем.

### 6.3 Общий разбор партии
Отдельный вызов: краткий итог (3–5 пунктов) по агрегатам: точность, ключевые моменты (наибольшие перепады), типичные ошибки.

## 9. Frontend (страницы)

1. `/` — импорт: вставить PGN или ник Lichess / Chess.com.
2. `/games` — список партий, фильтры, бейдж точности.
3. `/games/[id]` — **экран разбора**:
   - доска со стрелками (лучший ход — зелёная, сыгранный — по цвету класса);
   - eval-бар;
   - график оценки (клик → переход к ходу);
   - список ходов с иконками классов;
   - карточки игроков: точность, счётчики классов, точность по фазам;
   - панель хода: класс, «лучше было …», объяснение (ленивая загрузка), кнопка «показать линию» (проигрывание PV);
   - режим «Повтори лучший ход».
   - навигация стрелками клавиатуры, мобильная вёрстка.
4. `/stats` — дашборд: точность во времени, дебюты (винрейт + точность), фазы, частые мотивы ошибок.
5. `/puzzles` — пазлы из своих ошибок.

## Принятые решения (уточнения к ТЗ, 2026-10-15)

Имеют приоритет над формулировками выше.

- **Пользователь до сессии 10**: один dev-пользователь (сид в начальной миграции, `DEFAULT_USER_ID` из env). Все роуты получают пользователя только через dependency `get_current_user()` (`app/api/deps.py`); в сессии 10 меняется только она.
  - *Сессия 10*: режима без входа нет. Dev-пользователь остаётся записью без пароля (войти в неё нельзя), и **первый зарегистрированный получает её** — `id` тот же, поэтому партии, анализы, импорты и пазлы остаются на месте; меняются email, пароль и язык (`AUTH_CLAIM_DEV_USER`, по умолчанию `true`; захват — `SELECT … FOR UPDATE` записи без пароля). Ники Lichess / Chess.com сохраняются. `make e2e` отказывается запускаться, пока dev-пользователь не занят, — иначе его данные получил бы тестовый пользователь.
- **Auth (сессия 10)**: свой JWT (access + refresh), пароли — argon2. Supabase не используем.
  - Пароли — argon2id (`argon2-cffi`, параметры по умолчанию, пересчёт хеша при смене параметров), 8–128 символов; email — `EmailStr` в нижнем регистре (служебные домены вроде `.test` email-validator отклоняет). Неверный пароль и неизвестный email дают один и тот же 401 `invalid_credentials`, неизвестный email тоже проверяется по фиктивному хешу (время ответа не выдаёт регистрацию).
  - **Access** — JWT HS256 (`sub`, `typ=access`, `iat`, `exp`), 15 мин (`ACCESS_TOKEN_TTL_S`), в теле ответа; браузер держит его **только в памяти** вкладки (`web/src/lib/session.ts`): из памяти XSS его не унесёт так просто, как из localStorage, а после перезагрузки он восстанавливается обновлением. `JWT_SECRET` обязателен при `APP_ENV=prod`; в dev без него ключ случайный на процесс (после перезапуска API access-токены недействительны — клиент сам обновляется по refresh).
  - **Refresh** — случайные 256 бит в **httpOnly-cookie** `cr_refresh` (`Path=/api/v1/auth`, `SameSite=Lax`, `Secure` по `COOKIE_SECURE`), в БД — sha256 (`refresh_tokens`: `family_id`, `expires_at`, `replaced_at`, `revoked_at`), 30 дней. JavaScript cookie не видит, в остальные запросы API он не уходит. Обновление — ротация: предъявленный токен помечается заменённым, выдаётся следующий той же цепочки. Повтор заменённого токена позже `REFRESH_REUSE_GRACE_S` (10 с) — признак кражи: отзывается вся цепочка; в пределах окна (две вкладки обновились разом) — 401 `refresh_rotated` без отзыва, клиент повторяет с уже новым cookie. На клиенте обновление одно на все вкладки (Web Locks) и одно на вкладку (общий промис). Выход отзывает цепочку этого входа и удаляет cookie; другие устройства остаются в системе; уже выданный access-токен живёт до своего срока (клиент его забывает). Вход / выход в одной вкладке передаётся остальным через `BroadcastChannel`.
  - CORS — с `allow_credentials` и явными origin (`CORS_ORIGINS`); запросы auth идут с `credentials: "include"`, остальные — с заголовком `Authorization`. `localhost:3000` и `localhost:8001` — один сайт (порт в site не входит), поэтому cookie `SameSite=Lax` работает без HTTPS; если web и API на разных сайтах — `COOKIE_SAMESITE=none` + `COOKIE_SECURE=true`. Эндпоинты с cookie (register, login, refresh, logout) дополнительно отклоняют чужой `Origin` (403 `origin_forbidden`) — защита от CSRF на случай `SameSite=None`.
  - **SSE**: EventSource не умеет заголовки, поэтому `POST /analyses/{id}/events/token` выдаёт **stream-токен** — JWT `typ=stream` с `aid` анализа, 60 с (`STREAM_TOKEN_TTL_S`); `GET /analyses/{id}/events?token=…`. Токен проверяется при подключении (поток живёт дольше), годится только для одного анализа и только для чтения прогресса, в логах прокси бесполезен через минуту; uvicorn запущен с `--no-access-log`, свои логи пишут путь без query. Access-токен в query не принимается. Заголовок `Authorization` у этого эндпоинта тоже работает (curl, тесты). Переподключение после истечения токена получает 401 → клиент переходит на полинг (как и раньше при закрытом потоке).
  - API: `POST /auth/register {email, password, lang?}` (201), `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout` (204), `GET /auth/me`, `PATCH /auth/me {lang?, lichess_username?, chesscom_username?}` (менять только переданные поля; ник `""` / `null` — удалить). Ответ входа — `{access_token, token_type, expires_in, user}`, `Cache-Control: no-store`. Ошибки токена — 401 с `WWW-Authenticate: Bearer` и кодами `not_authenticated` / `token_expired` / `token_invalid`; на них клиент один раз обновляет токен и повторяет запрос.
  - Изоляция: каждый роут ищет данные с условием `user_id` текущего пользователя, чужие id — 404 того же вида, что несуществующие (`tests/test_isolation.py` — все роуты с id, списки, статистика, пазлы, повторный импорт того же PGN другим пользователем).
- **Лимиты (сессия 10)** (`app/api/ratelimit.py`): фиксированное окно в Redis (`INCR` + `EXPIRE NX`, ключ `rl:{вид}:{пользователь|IP}:{номер окна}`), значения `N/период` в конфиге (`RATE_LIMIT_*`, разбор — `app/core/rates.py`). Импорт (PGN, Lichess, Chess.com — общий лимит `import`, 30/ч), запуск анализа (`analyze`, 100/ч), LLM (`llm` — explain, explanations, summary, 300/ч) — на пользователя; вход (10/мин) и регистрация (10/ч) — на IP (`X-Forwarded-For` — только при `TRUST_FORWARDED_FOR`). Считаются только запросы, которые что-то стоят: повторный импорт того же ника, пока идёт прежний, и уже существующий анализ лимит не тратят; LLM-лимит не применяется при `LLM_PROVIDER=none` (шаблоны мгновенные). Превышение — 429, `Retry-After` (секунды до конца окна) и `params {scope, limit, period_s, retry_after}` для текста. Недоступный Redis лимиты не применяет (только лог). Окно фиксированное, а не скользящее: на стыке окон возможен двойной всплеск — для защиты от перебора и злоупотреблений этого достаточно, зато `Retry-After` точный.

  - *Уточнение (сессия 2, по замерам)*: MultiPV=3 везде — 69 с на партию 42 хода (depth 18, 4 процесса, Apple M1); MultiPV=1 — 21 с. Второй проход MultiPV=3 по кандидатам (лучший ход или Δ ≤ 2) не помог (72 с): кандидатов ~75%, а MultiPV=3 втрое дороже даже с тёплым хешем. Альтернативы нужны только `great` (сыгран лучший ход), `brilliant` их не требует. Реализовано: MultiPV=1 везде; если из позиции сыгран лучший ход, отдельным поиском **без этого хода** (`root_moves`) берутся ещё `ANALYSIS_MULTIPV − 1` линий — это эквивалент MultiPV=3 по содержанию. Итог: **40 с** на ту же партию, глубина не снижена (`app/engine/analyzer.py`).

- **Окно волатильности** (§4.4): `len` = число **полуходов** (оценок после ходов), как `cps.size` в lila. *Исправлено в сессии 2*: исходная формулировка «позиции (полуходы + 1)» расходится с Lichess; на 984 партиях с точностью от Lichess вариант с полуходами совпадает до округления в 100% случаев, вариант с позициями — нет. Стартовая позиция, если её оценки нет, = +0.15 (`Eval.Cp.initial` в lila).

- **Жертва (§4.5, сессия 3)** — уточнения по разбору известных партий:
  - «Под боем без адекватной защиты» = SEE лучшего легального взятия соперника > 0 (связки, рентген, взятия королём учитываются). Пешки и король не считаются.
  - Фигура, висевшая ещё **до последнего хода соперника** (он мог взять и не взял), — не новая жертва. Жертва — фигура, попавшая под бой этим ходом, или оставленная под только что созданной угрозой. Иначе каждый ход при давно висящей фигуре получал brilliant.
  - Соперник должен **взять** отданную фигуру в первые 2 своих хода PV1 (`SACRIFICE_ACCEPT_MOVES`); потеря материала считается после размена на этом поле. Иначе ход получал чужую жертву, сыгранную дальше в PV (12… Nxc3 у Фишера «наследовал» 17… Be6). Отказ от жертвы в PV1 (11… Na4 Фишера, 24. Rxd4 Каспарова на depth 18) — не жертва.
  - PV1 — продолжение лучшей линии позиции до хода, если сыгран лучший ход; для «почти лучшего» хода (Δ ≤ 2) — PV1 позиции после хода (`MoveEval.lines_after`).
- **`great`, «меняет результат»**: только для лучшего хода; категория результата (пороги 20/80, см. выше) лучшей линии MultiPV выше, чем второй.
- **`miss`**: Δ самого хода ≥ 10 после mistake/blunder соперника; флаг поверх класса.
- **Маты и brilliant**: win% упирается в 97,5 (cp обрезается до 1000), поэтому условие «win% < 97» отсекает позиции с оценкой ≳ +9,5 и форсированным матом: жертва ферзя с матом (16. Qb8+ Морфи, 9. Qd8+ Рети) — `great`/`best`, не `brilliant`. Это соответствует ТЗ.
- **Мотивы (§5, сессия 4)**:
  - Мотив описывает, что **делает сторона, совершающая ход**. Поэтому три контекста §5 обслуживает один набор детекторов: «игрок зевнул фигуру» = `hanging_piece` в ответе соперника (наказание), «упустил вилку» = `fork` в PV1 (упущено). `app/review/motifs/context.py`: `MoveMotifs(played, missed, refutation)`, `game_motifs` (позиция каждого хода — с ходом соперника в истории, по ней отличается взятие в ответ от взятия висящей фигуры).
  - `Motif.squares[i]` ↔ `pieces[i]`: первой — фигура ходящей стороны, затем цели; порядок для каждого типа описан в его модуле. `gain_cp` — выигрыш материала по первым 3 полуходам линии (+ доигранный размен на последнем поле), может быть отрицательным; `None` у матов и угрозы превращения. В `line` угроз (`mate_threat`, `promotion_threat`) `Move.null()` = «любой ход соперника».
  - Отдельные типы: `discovered_attack` / `discovered_check`, `removing_defender` / `overload`, `promotion` / `promotion_threat`, `mate_in_n` / `mate_threat`. N мата — число ходов матующей стороны в `line`.
  - Мат и угроза мата берутся из PV (PV при оценке «мат в N» доходит до мата), без отдельной оценки. Угроза мата — только новая: если мат в 1 был и до хода, мотива нет. Если ход сам ставит мат, от него остаются только `mate_in_n` / `back_rank`.
  - «Ценная цель» (вилка, вскрытое нападение) — король, фигура дороже нападающей или незащищённая фигура; пешки — не цели. Вилка / связка / линейный удар не засчитываются, если атакующую фигуру выгодно забрать; связка и линейный удар — только новые (сдвиг слона вдоль той же линии не считается).
  - `hanging_piece`: взятие, которое соперник не отбивает с выгодой (SEE ≥ стоимости взятой), кроме пешек и взятия в ответ на равноценное взятие.
  - `trapped_piece`: фигура под боем, любой её ход теряет материал по SEE, и до хода она не была поймана; при шахе не ищется.
  - `removing_defender` / `overload`: ход → ответ → взятие на другом поле с выигрышем материала; выигранная фигура стояла там до хода и не висела, а её защитник снят ходом / ушёл ответом.

Пока импорт того же ника (без учёта регистра) с той же площадки в queued / running — возвращается он (200), блокировка — строка пользователя `FOR UPDATE`. Каждая страница источника — отдельная транзакция со счётчиками; ошибка источника → failed с понятным текстом («Пользователь X не найден на Lichess»), уже сохранённые страницы остаются.
  - `external_id`: Lichess — id партии; Chess.com — `live/<id>` / `daily/<id>` из URL партии (у live и daily разные счётчики), иначе `uuid`. Дедупликация — тот же unique-ключ, что у PGN; `imported` — только новые (`INSERT … ON CONFLICT DO NOTHING RETURNING`).

Необязательный `LICHESS_TOKEN` ускоряет выгрузку (30 партий/с вместо 20).

- **Объяснения (сессия 7)**: факты (`explain/facts.py`) строятся из сохранённой строки `moves` (оценки, линии, мотивы) — движок не вызывается. Оценки в фактах — за сделавшего ход (`+1.20`, `#3`, `-#2`, `#` — поставил мат). «Лучше было» и упущенные мотивы — только у ошибок и miss: у brilliant / great с Δ ≤ 2 лучший ход формально другой, но подсказывать его неверно. Опровержение и `material_swing` (материал игрока после хода и 4 полуходов ответа, в пешках) — только у inaccuracy / mistake / blunder.
  - Проверка SAN (`explain/validate.py`): каждый токен английского SAN в ответе должен быть среди строк фактов (без учёта `+#` и `0-0`/`O-O`); голое поле (`e4`) допустимо, если поле есть в фактах; обозначение цели «Kg8» допустимо; русская нотация (`Кf3`) — всегда ошибка. Ответ с лишними ходами → один повтор с перечнем лишних ходов → шаблон.

- **Точность и рейтинг партии как у Chess.com (после сессии 8, по обратной связи пользователя: Chess.com — 77.2, у нас было 68.8)**:
  - Официальная точность: импорт Chess.com сохраняет `accuracies` из публичного API (есть у партий, разобранных на Chess.com) в `games.source_white_accuracy` / `source_black_accuracy`; повторный импорт дописывает их в уже сохранённые партии (`ON CONFLICT DO UPDATE … WHERE excluded не null`, новые считаются по `xmax = 0`).
  - Для остальных партий — своя точность «как у Chess.com» (`review/cc_accuracy.py`, `analyses.cc_white_accuracy` / `cc_black_accuracy`): win% = 50 + 50·(2/(1+e^(−k·cp)) − 1), cp обрезан до ±1000 (мат — ±1000); точность хода = (100+c)·e^(−b·Δwin%) − c; партия — степенное среднее с показателем p. Параметры подобраны Нелдером — Мидом (`scripts/fit_accuracy.py`) по 74 игроко-партиям с официальной точностью: `k=0.00130498, b=0.152752, c=5.90481, p=0.393014`. Ошибка на перекрёстной проверке (5 фолдов) — MAE 3.1 пункта против 5.8 у формулы Lichess. Точность Lichess (§4.4) по-прежнему считается и хранится (`white_accuracy` / `black_accuracy`) — по ней точность фаз.
  - Что показываем (`GameOut.accuracy_of`, `web/src/lib/accuracy.ts`, общий разбор): официальная → «как у Chess.com» → Lichess (старые анализы). В обзоре подпись: «по данным Chess.com» или «оценка по формуле, близкой к Chess.com».
  - Рейтинг партии («Game Rating», `review/game_rating.py`, `GameOut.game_rating`): ожидаемая точность игрока рейтинга r на Chess.com — E = a − b·e^(−r/c), своя кривая для bullet / blitz / rapid (daily — рапид + 12.3), подобрана по 20 500 парам (рейтинг, официальная точность) из публичных архивов Chess.com (`scripts/collect_chesscom_accuracy.py`, `scripts/fit_game_rating.py`). Рейтинг партии — обратная функция с шагом 50, в пределах 100…3200. Класс контроля — по база + 40·добавка (< 3 мин bullet, < 10 мин blitz). Грубо: Chess.com для партии пользователя дал 1750 / 1250, модель — 1650 / 1300.
  - Стрелки на доске как в Chess.com: лучший ход — синяя (если сыгран не он и ход не book / forced), угрозы после хода — красные (`web/src/lib/threats.ts`: фигуры сходившего, бьющие более ценную, незащищённую фигуру или короля; король — только незащищённые; не больше 4). Стрелки сыгранного хода нет (вместо §9 «лучший — зелёная, сыгранный — по цвету класса»).

- **Пазлы (сессия 9)** (`app/puzzles/`):
  - Источник — ход пользователя mistake / blunder или с флагом miss, где лучший ход другой. Позиция — `fen_before`, решение — PV1 до первого хода игрока, после которого (и ответа соперника из PV) материал игрока вырос на ≥ 2 пешки (`PUZZLE_MIN_GAIN`), или до мата; не длиннее 4 ходов игрока. Выигрыш считается от материала **до последнего хода соперника**, если он был больше: «отыграть» только что взятую фигуру — не пазл.
  - **Однозначность**: каждый ход игрока в решении (кроме последнего матующего — засчитывается любой мат) лучше второй линии MultiPV хотя бы на 10 win% (`PUZZLE_MIN_GAP` = `GREAT_MIN_GAP`, тот же «единственный ход», что у `great`), и движок в этой позиции согласен с PV. У ошибок в разборе обычно одна линия (MultiPV считается только там, где сыгран лучший ход), поэтому вторая добирается движком через `Analyzer.analyse(played={ход})` на глубине анализа, с кэшем в `position_evals`.
  - **Пазлы «единственный ход»** (расширение по данным пользователя): из 161 ошибки только у ~35 лучшая линия выигрывает материал, и тактический пазл получался 1. Если линия материал не выигрывает, но лучший ход однозначен (то же правило разрыва ≥ 10), пазл — один этот ход, тема `only_move`. Итог на партиях пользователя: 46 пазлов из 43 разборов.
  - Темы — типы мотивов упущенной линии (`motifs.missed`) + `mate_in_n`, если решение кончается матом.
  - Идемпотентность: уникальность `(user_id, fen)`; повторная генерация и повторный анализ партии обновляют только `move_id` (состояние повторения сохраняется). Генерация — в воркере сразу после сохранения разбора (сбой только логируется; задача, прерванная на генерации, при повторе видит done и генерирует снова) и скриптом `scripts/generate_puzzles.py` для готовых анализов.
  - **Повторение — коробки Лейтнера** (`srs.py`): 0 — новый или решённый неверно, 1…5 — показ через 1 / 3 / 7 / 16 / 35 дней. Без подсказки — коробка +1; с подсказкой — не растёт (но не ниже 1); неверный ход или «Решение» — коробка 0 и повтор через 10 минут (в той же сессии, после других). `GET /puzzles/next` — сначала пора повторить (по сроку), затем новые (из более свежих партий); `exclude` — пропущенные.
  - Проверка на сервере, пошагово: `POST /puzzles/{id}/attempt {moves_uci, hint_used, gave_up}` с ходами с начала пазла; пока верно — `continue` + ответ соперника (не записывается), затем `solved` / `failed` с верным ходом, решением (UCI и SAN), следующим повторением и серией. Решение клиенту до конца попытки не отдаётся; подсказка — поле фигуры (`hints`). Превращение засчитывается по клеткам (с доски — всегда ферзь). Попытки — в `puzzle_attempts`, серия — решённые после последней неудачной.

Английские названия классов — как в Game Review Chess.com (Brilliant, Great, Best, Excellent, Good, Book, Inaccuracy, Mistake, Miss, Blunder).
  - Заголовок вкладки — `DocumentTitle` (клиентский `document.title`); `title` в metadata нет: второй `<title>` от Next перебивал бы его.
- **Frontend: вход (сессия 10)**: группы маршрутов `app/(auth)` (вход, регистрация — без навигации, `GuestOnly`: вошедшего отправляет на `?next=`) и `app/(app)` (всё остальное, `RequireAuth` → `/login?next=…`, после явного «Выйти» — без `next`). `AuthProvider` в корневом layout при открытии страницы обновляет сессию по cookie; пока ответа нет, вместо страницы — заставка (поэтому язык и вход известны до первого показа текста, без мигания). Следствие: страницы за входом не попадают в серверный пререндер (dev-оверлей Next пишет «segment dropped from rendering» — это ожидаемо: все данные и так грузятся в браузере). URL в «воротах» — из `window.location`, а не `usePathname`, чтобы не требовать `<Suspense>`. Профиль — `/profile` (email, язык, ники, выход); в навигации — буква email внизу колонки (на телефоне — справа в полосе) и «Выйти» (на телефоне — только в профиле). Next держит ушедшие страницы в `<Activity>`: в DOM может быть сразу и форма входа, и форма регистрации (в e2e — только `:visible` поля).
- **Playwright (сессия 10)**: один сквозной smoke `web/e2e/smoke.spec.ts` по поднятому стеку (регистрация → выход → вход → ник в профиле → вставка PGN → анализ по SSE → разбор хода с объяснением → статистика → пазл, решённый кликами → выход → редирект на вход). Партия подобрана так, что пазл гарантирован: белые пропускают мат в один ход (4. d3 вместо Qxf7#). Браузер — установленный Chrome (`channel: "chrome"`), Chromium Playwright не скачивается; локаль `ru-RU`. Каждый прогон — новый пользователь `e2e-…@example.com`, `make e2e` удаляет их после прогона.

- **Движок в браузере (сессия 11)**: Stockfish.js 19 (Nathan Rugg / Chess.com, GPL-3.0), сборка **lite single-threaded** — 1,8 МБ, без SharedArrayBuffer, поэтому не нужны заголовки COOP/COEP (они ломали бы загрузку ресурсов с других источников). Полная сеть — 99 МБ, её загрузка дольше самого анализа. Файлы не изменены, лежат в `web/public/engine/` (с `COPYING.txt`), собираются `web/scripts/fetch-engine.mjs` из npm-пакета закреплённой версии со сверкой sha512 реестра; npm-зависимостью не подключаем (205 МБ ради двух файлов). Имена файлов с версией — кэш браузера не отдаст старый движок.
  - **Анализ партии** (`web/src/lib/engine/`): пул Web Workers (ядра − 1, не больше 4, хеш 32 МБ на воркер). Схема — как `Analyzer` на сервере: каждая уникальная позиция с MultiPV=1, а если из неё сыгран лучший ход — ещё `MultiPV − 1` линий поиском `searchmoves` без него; глубина и MultiPV — из `GET /engine/config` (`ANALYSIS_DEPTH`, `ANALYSIS_MULTIPV`). Поиск ограничен ещё и 8 с (`go depth … movetime 8000`): альтернативы к матующему ходу (все прочие ходы проигрывают) lite-сеть на глубине 18 считает десятки секунд — такая позиция сохраняется с меньшей глубиной. Партия в 4 хода из e2e (depth 18) — несколько секунд; Оперная партия (34 позиции) до введения предела упиралась в одну такую позицию.
  - **Разбор — на сервере, общей логикой `review/`**: `POST /games/{id}/browser-analysis {depth, engine, positions}` — оценки всех позиций в формате кэша `position_evals` (`{depth, lines: [{cp | mate, pv: [uci]}]}`, null — у позиций без ходов). Сервер проверяет оценки (`app/engine/external.py`: число позиций, ровно одна из cp / mate, mate ≠ 0, легальность каждого хода линий, различные первые ходы, до 5 линий и 64 ходов), финальные позиции оценивает сам (`terminal_eval`), затем `review_game` → те же строки `moves`, что у воркера, и анализ `status=done`, `runner=browser`, `engine_version` = `id name` движка («Stockfish 19 Lite WASM»). Тест сверяет: одни и те же оценки через воркер и через браузер дают одинаковый разбор поле в поле. Лимит `browser` (300/ч на пользователя); `depth < BROWSER_MIN_DEPTH` (10) — 422 `depth_too_low`, плохие оценки — 422 `engine_data_invalid` с номером позиции.
  - Доверие: подделать оценки пользователь может только для своей партии (влияет на его разбор и статистику); в общий кэш `position_evals` оценки из браузера **не пишутся**. Последний анализ партии — показываемый, поэтому браузерный анализ заменяет прежний на экране. `POST /games/{id}/analyze` переиспользует только серверные анализы (`runner=server`): после анализа в браузере можно запросить серверный той же глубины.
  - **Пазлы**: генерации нужны вторые линии движка в позициях решений, а их знает только браузер. `collect_probes` прогоняет ту же `generate_puzzles` с записывающим анализатором, который отвечает «ход единственный», — так собираются все позиции, которые проверка спросила бы у движка. Ответ на сохранение содержит `puzzle_probes`; браузер считает их (MultiPV=2 по той же схеме) и шлёт в `POST /analyses/{id}/browser-puzzles` — пазлы строит та же `generate_puzzles` с ответами браузера вместо движка (`ProbeAnalyser`; позиции без ответа пазла не дают). Если проб нет (решения — мат в 1), пазлы строятся сразу при сохранении. На партии пользователя сервер и браузер дали одинаковый результат.
  - UI: перед анализом — переключатель «Где считать: На сервере / В браузере» (по умолчанию сервер; выбор — в localStorage), прогресс браузерного анализа — тем же индикатором, кнопка «Остановить»; в обзоре — «движок · где · глубина». Пазлы досчитываются после показа разбора; их сбой разбор не ломает.
- **Режим исследования (сессия 11)**: на доске разбора свой ход (перетаскиванием или кликами по клеткам) в режиме партии; ход, совпавший со следующим ходом партии, — просто шаг вперёд, иначе — линия исследования от этой позиции (ходы списком, ← → по ним, новый ход отрезает хвост, Esc / «Вернуться к партии»). Оценка, лучшая линия (10 ходов) и синяя стрелка лучшего хода, «Сделать лучший ход». Движок — переключатель «Браузер / Сервер» (по умолчанию браузер, если есть WASM; выбор в localStorage): в браузере — один воркер на экран, оценка уточняется по мере углубления до `EXPLORE_DEPTH`; через API — `POST /engine/analyse {fen}` (пауза 300 мс перед запросом, кэш по FEN на вкладку, отмена при уходе с позиции).
  - API считает **своим пулом Stockfish в процессе API** (`LazyEnginePool`, `EXPLORE_POOL_SIZE` = 1, процессы стартуют при первом запросе): через очередь воркера ответ ждал бы окончания анализов партий. Оценки берутся из общего кэша `position_evals` и пишутся в него (серверные). Глубина `EXPLORE_DEPTH` (18), лимит `explore` (600/ч на пользователя); неверный FEN — 422 `invalid_fen`, нет Stockfish — 503 `engine_unavailable` (API без Stockfish стартует и работает). Финальная позиция — пустые линии.
- **Рейтинговая группа (сессия 11)**: средняя точность игроков рейтинга r и контроля — кривые `review/game_rating.py` (`group_accuracy`, та же модель, что «рейтинг партии»). Кривые подобраны по рейтингам и официальной точности **Chess.com**, поэтому сравнение — только для партий Chess.com и только с точностью «как у Chess.com» (официальной или нашей); рейтинги Lichess на другой шкале, точность Lichess — другая формула — для них группы нет.
  - Партия: `GameOut.group_accuracy {white, black}` — по рейтингу каждого игрока; на плашках «ср. 77.6» рядом с точностью (на телефоне скрыто — не помещается), в обзоре строка «Средняя группы».
  - `/stats`: у точек графика `rating`, `group_accuracy` и `group_moving_avg` (скользящее среднее группы, то же окно 10) — пунктирная линия «Средняя для вашего рейтинга» и строка в подсказке; блок «Вы и ваша рейтинговая группа» (`rating_groups`) — по контролям: партий, средний рейтинг, ваша средняя точность, средняя группы, разница. Всё в SQL: `group_accuracy_sql` — копия формулы, совпадение с Python проверяет тест. На партиях пользователя: рапид 1714 — 79.4 против 77.9, блиц 1124 — 77.8 против 73.0.
- **Публичные ссылки (сессия 11)**: `games.share_token` (`secrets.token_urlsafe(16)`, 128 бит, уникальный). Владелец: `POST /games/{id}/share` → `{token, url}` (идемпотентно), `GET` — текущая ссылка (404 `share_not_found`, если нет), `DELETE` — отзыв (старая ссылка перестаёт работать, новая — другой токен). Без входа: `GET /shared/{token}` — то же, что `GET /games/{id}`; `POST /shared/{token}/moves/{move_id}/explain {lang}` и `GET /shared/{token}/summary?lang=` (ход — только из последнего анализа этой партии; лимит LLM по IP, шаблоны без лимита). SSE для ссылок нет — страница опрашивает раз в 3 с, пока анализ идёт.
  - Web: кнопка «Поделиться» в шапке панели разбора (ссылка копируется сразу, адрес — origin браузера; «Закрыть доступ»), страница `/share/[token]` вне групп `(app)` / `(auth)` — без входа и навигации, шапка с логотипом, языком и «Разобрать свои партии» (вошедшему — «Разбор партий»). Тот же экран разбора, только чтение: без кнопки запуска анализа и «Поделиться»; объяснения и итог — через контекст `ReviewSource` (свой API или публичный, язык — интерфейса гостя); `?ply=N` открывает ход.
- **Telegram-бот (сессия 11)** (`app/bot/`, сервис `bot` в compose по профилю, `make bot`): прислал ник Lichess / Chess.com → разбор последней партии. Собственный минимальный клиент Bot API на httpx (без новых зависимостей), long polling (вебхук и открытый порт не нужны).
  - **Партии бота принадлежат системному пользователю** `BOT_USER_ID` (…0002, сид в миграции, без пароля): партии площадок публичны, одна партия по разным запросам сохраняется и анализируется один раз (unique(source, external_id, user_id)). Ссылка в ответе — публичная `/share/{token}` (ссылки на ошибки — с `?ply=`). Аккаунты Telegram и приложения не связываются. Пазлы для пользователя бота не генерируются (`generate_puzzles(skip_users=…)` — их никто не решает).
  - Источники: Lichess — последняя партия (`max=1`); Chess.com — два последних месяца, в которых есть партии (по списку архивов, а не по календарю), новые первыми. Анализ — как `POST /games/{id}/analyze` (переиспользуется не-failed серверный анализ глубины `ANALYSIS_DEPTH`, лимит `analyze` не тратится); ожидание — подписка на `analysis:{id}:events` до постановки в очередь + перепроверка в БД каждые 5 с, не дольше `BOT_ANALYSIS_TIMEOUT_S` (дальше — ответ «ещё считается» со ссылкой).
  - Ответ (HTML Telegram, без превью ссылок): игроки и рейтинги, результат для спросившего, контроль, площадка, дата, дебют; точность (та же, что на плашках) и рейтинг партии; до 3 ошибок спросившего (mistake / blunder / miss с наибольшим падением win%, в порядке партии); итог `Explainer.summarize` на языке чата для цвета спросившего; ссылка на полный разбор. «Анализирую…» отправляется сразу и затем редактируется результатом.
  - Команды: `/start`, `/help`, `/lang ru|en`, `/lichess <ник>`, `/chesscom <ник>`, просто ник — кнопки площадок (callback `lichess:<ник>`); в группах — только команды. Язык чата — `telegram_chats.lang` (новый чат — `ru`, если `language_code` начинается с `ru`, иначе `en`). Лимит `bot` (20/ч) — на чат и на каждый запрос разбора (в том числе неудачный — защита площадок), справка и кнопки не считаются. Одновременных разборов — `BOT_MAX_CONCURRENCY`; SIGTERM — 8 с на идущие ответы. Токен — часть URL Bot API, поэтому логгер httpx приглушён, а URL в тексты ошибок не попадает.
  - Ограничения: живого прогона против настоящего Telegram нет (нет токена) — проверено сквозным прогоном `python -m app.bot` против локального фейкового Bot API с настоящими Chess.com / Lichess, воркером со Stockfish, Redis и БД, и тестами на фейках. С `PUBLIC_WEB_URL=localhost` ссылки из Telegram открываются только на этой машине. Прогресс анализа в чате не показывается.
- **Playwright (сессия 11)**: второй сценарий `web/e2e/engine.spec.ts` — регистрация → вставка PGN → анализ движком в браузере (выбор — через localStorage до загрузки страницы) → обзор «· в браузере ·» → исследование (1… d5 кликами, оценка движком браузера, затем сервера, «Сделать лучший ход») → пазл из ошибки (мат в 1, без проб) → «Поделиться» → ссылка открывается в чистом контексте без входа → «Закрыть доступ» → «Ссылка недействительна». Тесты идут по одному (`workers: 1`): анализ в браузере занимает ядра; `make e2e` перед прогоном обнуляет счётчики лимитов входа и регистрации (каждый прогон регистрирует пользователей).
