# Chess Review — ТЗ и архитектура

> Документ для исполнителя (Claude Code / новая сессия). Работай строго по сессиям ниже. В конце каждой сессии: тесты зелёные, обнови раздел «Статус» в конце файла, сделай коммит.

## 1. Цель продукта

Веб-приложение для разбора шахматных партий, аналог Chess.com Game Review, но с open-source движком и честными объяснениями:
- точность игрока за партию и по фазам;
- классификация каждого хода (brilliant → blunder);
- объяснение ошибок и тактик человеческим языком, **заземлённое на анализ движка** (без галлюцинаций);
- импорт партий с Lichess / Chess.com / PGN;
- статистика по многим партиям и пазлы из собственных ошибок.

Языки интерфейса и объяснений: RU / EN (UZ — опционально позже).

### Модули backend (`backend/app/`)
- `api/` — роуты: `games`, `analysis`, `imports`, `stats`, `puzzles`, `auth`.
- `core/` — config (pydantic-settings), логирование, DI.
- `db/` — модели, сессии, миграции.
- `engine/` — пул Stockfish-процессов (`EnginePool`), анализ позиции, кэш по FEN.
- `review/` — **чистая доменная логика без I/O**:
  - `winprob.py` — cp/mate → win%;
  - `accuracy.py` — точность хода и партии;
  - `classify.py` — классификация ходов;
  - `phases.py` — дебют / миттельшпиль / эндшпиль;
  - `openings.py` — определение дебюта (ECO), «книжные» ходы;
  - `motifs/` — детекторы тактических мотивов;
  - `pipeline.py` — оркестрация анализа партии.
- `explain/` — построение фактов для LLM, промпты, провайдеры, кэш.
- `importers/` — Lichess API, Chess.com public API, PGN.
- `workers/` — ARQ-задачи.

### Ключевой принцип
Вся логика в `review/` и `explain/facts.py` — детерминированная и покрыта юнит-тестами на фиксированных FEN/PGN. LLM получает **только проверенные факты** и переводит их в текст. LLM не оценивает позиции и не придумывает варианты.

## 4. Доменная логика (точные формулы)

### 4.1 Оценка движка
- Анализ каждой позиции: `depth=18` (настраиваемо), `MultiPV=3`, `Threads` и `Hash` из конфига.
- Оценка всегда нормализуется к точке зрения **игрока, делающего ход**.
- Мат: `mate in N` → cp = ±(10000 − N·10) для win%, но в UI показывать `#N`.
- Кэш: таблица `position_evals` (ключ: FEN без счётчиков ходов + depth + multipv).

### 4.2 Win% (формула Lichess)
```
win% = 50 + 50 * (2 / (1 + exp(-0.00368208 * cp)) - 1)
```
cp обрезать до [-1000, 1000].

### 4.3 Точность хода
```
Δ = max(0, win%_before - win%_after)      # с точки зрения ходящего
acc = 103.1668 * exp(-0.04354 * Δ) - 3.1669
acc = clamp(acc, 0, 100)
```

### 4.4 Точность партии (как у Lichess)
- Окно волатильности: размер = clamp(len(moves)/10, 2, 8).
- Вес хода = stdev(win%) в окне, clamp к [0.5, 12].
- `game_acc = (weighted_mean(acc, weights) + harmonic_mean(acc)) / 2`.
- Отдельно считать точность по фазам.

### 4.5 Классификация ходов
Порядок проверок важен (первое совпадение):

| Класс | Условие |
|---|---|
| `book` | позиция после хода есть в книге дебютов и ход ≤ 15-го |
| `forced` | единственный легальный ход |
| `brilliant` | ход = best или Δ ≤ 2, **и** является жертвой (см. ниже), **и** позиция после хода не хуже −1.0 для ходящего, **и** до хода игрок не был уже в подавляющем выигрыше (win% < 97) |
| `great` | ход = best, и второй вариант MultiPV хуже на ≥ 10 win% (единственный ход), или ход меняет результат (проигрыш → ничья, ничья → выигрыш) |
| `best` | совпадает с PV1 |
| `excellent` | Δ ≤ 2 |
| `good` | Δ ≤ 5 |
| `inaccuracy` | Δ ≤ 10 |
| `mistake` | Δ ≤ 20 |
| `blunder` | Δ > 20 |
| `miss` | дополнительный флаг: соперник ошибся (prev move mistake/blunder), а игрок не наказал (Δ ≥ 10 относительно лучшей линии) |

**Жертва**: после хода SEE (static exchange evaluation) на отданной фигуре отрицательный, или фигура остаётся под боем без адекватной защиты, и в PV1 материал временно падает минимум на 2 пешки, но оценка держится. Пешечные жертвы `brilliant` не дают.

Все пороги вынести в конфиг `review/thresholds.py`.

### 4.6 Фазы
- Дебют: до выхода из книги или до 12-го хода, что раньше, пока не разменяны ферзи.
- Эндшпиль: суммарный материал без пешек ≤ 13 (Ф=9, Л=5, С/К=3) или ферзей нет и лёгких/тяжёлых фигур ≤ 6.
- Иначе миттельшпиль.

### 4.7 Дебюты
- Встроить TSV-базу дебютов Lichess (`lichess-org/chess-openings`, CC0): ECO, название, EPD.
- Определение дебюта: самое глубокое совпадение по EPD.

## 5. Тактические мотивы (`review/motifs/`)

Каждый детектор — чистая функция `detect(board_before, move, pv) -> list[Motif]`, где `Motif {type, squares, pieces, gain_cp, line}`.

Обязательные (MVP):
1. **hanging_piece** — фигура без защиты под боем / зевок фигуры.
2. **fork** — одна фигура атакует ≥ 2 ценных цели (с учётом шаха).
3. **pin** — абсолютная / относительная связка.
4. **skewer** — линейный удар.
5. **discovered_attack** / discovered check.
6. **double_check**.
7. **mate_threat / mate_in_n** — из оценки движка + PV.
8. **back_rank** — мат / угроза по последней горизонтали.
9. **trapped_piece** — у фигуры нет безопасных полей.
10. **removing_defender** / overload.
11. **promotion** — продвижение / угроза превращения.

Детекторы применяются: (а) к ходу игрока, (б) к лучшей линии PV1 (что упущено), (в) к ответу соперника в PV после ошибки (чем наказывается).

Для каждого детектора — ≥ 3 тестовых FEN (положительные) и ≥ 2 отрицательных.

## 6. Объяснения (`explain/`)

### 6.1 Факты
`facts.py` строит JSON на каждый ход с классом ≥ inaccuracy, а также для brilliant/great/miss:
```json
{
  "move_san": "Nf3", "class": "blunder", "eval_before": "+0.8", "eval_after": "-3.2",
  "best_move_san": "Bxf7+", "best_line_san": ["Bxf7+", "Kxf7", "Ng5+"],
  "refutation_line_san": ["Qb6", "..."],
  "motifs_in_refutation": [{"type": "fork", "piece": "N", "square": "e7", "targets": ["Kg8","Rc8"]}],
  "motifs_missed": [...], "material_swing": "-5", "phase": "middlegame"
}
```

### 6.2 LLM
- Интерфейс `LLMProvider.generate(system, user, max_tokens) -> str`, реализации Gemini/OpenAI/Anthropic, выбор через env.
- Системный промпт: «Ты шахматный тренер. Объясняй **только** на основе фактов. Не придумывай ходы и варианты. 2–4 предложения. Уровень — клубный игрок. Язык: {lang}.»
- Валидация вывода: все SAN-ходы в ответе должны присутствовать в фактах; иначе ретрай 1 раз, затем шаблонное объяснение (fallback без LLM).
- Шаблонные объяснения (`templates.py`) на каждый мотив — работают без LLM вообще.
- Кэш по хешу фактов + язык. Генерация **ленивая**: по клику / при открытии ревью, батчем.

### 6.3 Общий разбор партии
Отдельный вызов: краткий итог (3–5 пунктов) по агрегатам: точность, ключевые моменты (наибольшие перепады), типичные ошибки.

## 9. Frontend (страницы)

1. `/` — импорт: вставить PGN или ник Lichess / Chess.com.
2. `/games` — список партий, фильтры, бейдж точности.
3. `/games/[id]` — **экран разбора**:
   - доска со стрелками (лучший ход — зелёная, сыгранный — по цвету класса);
   - eval-бар;
   - график оценки (клик → переход к ходу);
   - список ходов с иконками классов;
   - карточки игроков: точность, счётчики классов, точность по фазам;
   - панель хода: класс, «лучше было …», объяснение (ленивая загрузка), кнопка «показать линию» (проигрывание PV);
   - режим «Повтори лучший ход».
   - навигация стрелками клавиатуры, мобильная вёрстка.
4. `/stats` — дашборд: точность во времени, дебюты (винрейт + точность), фазы, частые мотивы ошибок.
5. `/puzzles` — пазлы из своих ошибок.

## Принятые решения (уточнения к ТЗ, 2026-10-15)

Имеют приоритет над формулировками выше.

- **Пользователь до сессии 10**: один dev-пользователь (сид в начальной миграции, `DEFAULT_USER_ID` из env). Все роуты получают пользователя только через dependency `get_current_user()` (`app/api/deps.py`); в сессии 10 меняется только она.
- **Auth (сессия 10)**: свой JWT (access + refresh), пароли — argon2. Supabase не используем.
- **Книга дебютов**: в MVP только `lichess-org/chess-openings`. Проверка «книжного» хода — через интерфейс `OpeningBook.is_book(board, move)`, чтобы позже подключить Polyglot без переделок.
- **LLM**: первый провайдер — Gemini (самая дешёвая актуальная Flash-модель), выбор через `LLM_PROVIDER`. Без ключа (`LLM_PROVIDER=none`) работают шаблонные объяснения, и это полноценный рабочий режим, а не заглушка.
- **Frontend**: последняя стабильная версия Next.js (сейчас 16), App Router.
- **Точность хода**: константы и формула берутся из исходников lila (`AccuracyPercent.scala`), включая «uncertainty bonus» +1 до clamp, если он там есть. Тест: партия с Lichess, их точность — эталон, допуск ±1.
- **Производительность**: анализируется каждая позиция один раз (оценка «после хода» = оценка следующей позиции). Если не укладываемся в 60 с: сначала MultiPV=1 везде и MultiPV=3 только там, где нужно для great/brilliant (ход совпал с лучшим или Δ мал); снижать глубину — только после этого.
  - *Уточнение (сессия 2, по замерам)*: MultiPV=3 везде — 69 с на партию 42 хода (depth 18, 4 процесса, Apple M1); MultiPV=1 — 21 с. Второй проход MultiPV=3 по кандидатам (лучший ход или Δ ≤ 2) не помог (72 с): кандидатов ~75%, а MultiPV=3 втрое дороже даже с тёплым хешем. Альтернативы нужны только `great` (сыгран лучший ход), `brilliant` их не требует. Реализовано: MultiPV=1 везде; если из позиции сыгран лучший ход, отдельным поиском **без этого хода** (`root_moves`) берутся ещё `ANALYSIS_MULTIPV − 1` линий — это эквивалент MultiPV=3 по содержанию. Итог: **40 с** на ту же партию, глубина не снижена (`app/engine/analyzer.py`).
- **Номера ходов** («ход ≤ 15», «12-й ход») — полные ходы, не полуходы.
- **Окно волатильности** (§4.4): `len` = число **полуходов** (оценок после ходов), как `cps.size` в lila. *Исправлено в сессии 2*: исходная формулировка «позиции (полуходы + 1)» расходится с Lichess; на 984 партиях с точностью от Lichess вариант с полуходами совпадает до округления в 100% случаев, вариант с позициями — нет. Стартовая позиция, если её оценки нет, = +0.15 (`Eval.Cp.initial` в lila).
- **Эндшпиль** (§4.6): материал считается за обе стороны; фазы идут только вперёд.
- **«Меняет результат»** для `great`: проигрыш — win% < 20, ничья — 20–80, выигрыш — > 80; пороги в `review/thresholds.py`.
- **Ответы LLM**: ходы всегда в английском SAN, на любом языке объяснения.
- **PGN-партии**: `external_id` = хеш нормализованного PGN.
- **Точность по фазам** (сессия 2): та же формула §4.4 по ходам фазы, веса волатильности — общие по партии. С фазовой точностью Lichess не сверяется: у них другое деление на фазы.
- **Доменные перечисления** (`MoveClass`, `Phase`) и типы оценок живут в `app/review/types.py`; `db/models.py` импортирует их оттуда. Оценки — `chess.engine.Score` (`Mate(0)` — мат на доске стороне на ходу, `MateGiven` — поставленный).
- **Книга дебютов (сессия 3)**: книжная — любая позиция на линиях базы Lichess, включая промежуточные без названия (их ≈ половина); сравнение по EPD, переходы распознаются. Класс `book` — ход в книжную позицию на ходу ≤ 15; для фаз «дебют до выхода из книги» — непрерывная серия книжных полуходов с начала (`OpeningsDB.book_plies`). Дебют партии — самая глубокая позиция партии **с названием**. Данные — `app/review/data/openings.tsv` (eco, name, pgn, uci, epd), собираются `scripts/build_openings.py` из закреплённого коммита репозитория.
- **Жертва (§4.5, сессия 3)** — уточнения по разбору известных партий:
  - «Под боем без адекватной защиты» = SEE лучшего легального взятия соперника > 0 (связки, рентген, взятия королём учитываются). Пешки и король не считаются.
  - Фигура, висевшая ещё **до последнего хода соперника** (он мог взять и не взял), — не новая жертва. Жертва — фигура, попавшая под бой этим ходом, или оставленная под только что созданной угрозой. Иначе каждый ход при давно висящей фигуре получал brilliant.
  - Соперник должен **взять** отданную фигуру в первые 2 своих хода PV1 (`SACRIFICE_ACCEPT_MOVES`); потеря материала считается после размена на этом поле. Иначе ход получал чужую жертву, сыгранную дальше в PV (12… Nxc3 у Фишера «наследовал» 17… Be6). Отказ от жертвы в PV1 (11… Na4 Фишера, 24. Rxd4 Каспарова на depth 18) — не жертва.
  - PV1 — продолжение лучшей линии позиции до хода, если сыгран лучший ход; для «почти лучшего» хода (Δ ≤ 2) — PV1 позиции после хода (`MoveEval.lines_after`).
- **`great`, «меняет результат»**: только для лучшего хода; категория результата (пороги 20/80, см. выше) лучшей линии MultiPV выше, чем второй.
- **`miss`**: Δ самого хода ≥ 10 после mistake/blunder соперника; флаг поверх класса.
- **Маты и brilliant**: win% упирается в 97,5 (cp обрезается до 1000), поэтому условие «win% < 97» отсекает позиции с оценкой ≳ +9,5 и форсированным матом: жертва ферзя с матом (16. Qb8+ Морфи, 9. Qd8+ Рети) — `great`/`best`, не `brilliant`. Это соответствует ТЗ.
- **Мотивы (§5, сессия 4)**:
  - Мотив описывает, что **делает сторона, совершающая ход**. Поэтому три контекста §5 обслуживает один набор детекторов: «игрок зевнул фигуру» = `hanging_piece` в ответе соперника (наказание), «упустил вилку» = `fork` в PV1 (упущено). `app/review/motifs/context.py`: `MoveMotifs(played, missed, refutation)`, `game_motifs` (позиция каждого хода — с ходом соперника в истории, по ней отличается взятие в ответ от взятия висящей фигуры).
  - `Motif.squares[i]` ↔ `pieces[i]`: первой — фигура ходящей стороны, затем цели; порядок для каждого типа описан в его модуле. `gain_cp` — выигрыш материала по первым 3 полуходам линии (+ доигранный размен на последнем поле), может быть отрицательным; `None` у матов и угрозы превращения. В `line` угроз (`mate_threat`, `promotion_threat`) `Move.null()` = «любой ход соперника».
  - Отдельные типы: `discovered_attack` / `discovered_check`, `removing_defender` / `overload`, `promotion` / `promotion_threat`, `mate_in_n` / `mate_threat`. N мата — число ходов матующей стороны в `line`.
  - Мат и угроза мата берутся из PV (PV при оценке «мат в N» доходит до мата), без отдельной оценки. Угроза мата — только новая: если мат в 1 был и до хода, мотива нет. Если ход сам ставит мат, от него остаются только `mate_in_n` / `back_rank`.
  - «Ценная цель» (вилка, вскрытое нападение) — король, фигура дороже нападающей или незащищённая фигура; пешки — не цели. Вилка / связка / линейный удар не засчитываются, если атакующую фигуру выгодно забрать; связка и линейный удар — только новые (сдвиг слона вдоль той же линии не считается).
  - `hanging_piece`: взятие, которое соперник не отбивает с выгодой (SEE ≥ стоимости взятой), кроме пешек и взятия в ответ на равноценное взятие.
  - `trapped_piece`: фигура под боем, любой её ход теряет материал по SEE, и до хода она не была поймана; при шахе не ищется.
  - `removing_defender` / `overload`: ход → ответ → взятие на другом поле с выигрышем материала; выигранная фигура стояла там до хода и не висела, а её защитник снят ходом / ушёл ответом.
- **Pipeline (сессия 5)**: `review/pipeline.py` — `review_game` (чистая функция: оценки позиций → точность, классы, мотивы, дебют) и `analyse_game` (оценки берёт у анализатора через протокол `GameAnalyser`, сам разбор ~1 с CPU уводит в `asyncio.to_thread`). CLI работает через тот же pipeline.
- **Хранение разбора (сессия 5)**: добавлена колонка `moves.reply_pv` — лучшая линия соперника после хода (опровержение); у последнего хода партии её иначе не восстановить. Форматы JSON-полей `pv` / `multipv` / `reply_pv` / `motifs` описаны в `app/workers/serialize.py`: линия — `[{uci, san}]` (нулевой ход угрозы — `{"uci": "0000", "san": "--"}`), мотивы — `{played, missed, refutation, sacrifice}`, клетки и фигуры — `"e7"` / `"N"` (регистр — цвет). `mate_after == 0` — ход поставил мат. API отдаёт класс хода полем `class`, плюс вычисляемые `color` и `fullmove`.
- **Импорт PGN (сессия 5)**: хеш (`external_id`) — sha256 от 7 обязательных тегов + SetUp/FEN + SAN основной линии; хранится PGN с заголовками и комментариями (`%clk`, `%eval`), без вариантов. Отклоняются (422) ошибки разбора, варианты (включая Chess960) и партии без ходов; за запрос — до 100 партий и 1 МБ текста. Повторный импорт возвращает уже сохранённые партии. Дебют — своей базой при импорте (тег ECO не используется). `played_at` — `UTCDate`/`UTCTime`, иначе `Date`/`Time` как UTC; неполная дата → null. Цвет пользователя для PGN — по его нику Lichess / Chess.com (`importers/store.py`, общий для сессии 6).
- **Запуск анализа (сессия 5)**: `POST /games/{id}/analyze` возвращает уже существующий анализ той же глубины в статусе queued / running / done (200), иначе создаёт новый (202); failed не переиспользуется. Партия блокируется `FOR UPDATE` — двойной клик не создаёт два анализа. Анализ в queued ставится в очередь повторно (ARQ не дублирует задачу с тем же id `analysis:{id}`), чтобы пережить потерю очереди. Очередь недоступна → 503, анализ — failed.
- **Воркер (сессия 5)**: задача `analyze_game` идемпотентна — удаляет ходы незавершённого анализа, готовый не трогает; `max_tries=3`, таймаут `ANALYSIS_JOB_TIMEOUT_S`; отмена или таймаут → failed «Анализ прерван», исключение → failed с текстом ошибки. `WORKER_MAX_JOBS` партий одновременно делят один пул движков; кэш оценок — `position_evals`.
- **Прогресс и SSE (сессия 5)**: `done/total` — уникальные позиции, а не полуходы (повторы считаются один раз, финальные позиции движок не анализирует). Воркер пишет последнее состояние в ключ Redis `analysis:{id}:progress` (TTL 1 ч) и публикует в канал `analysis:{id}:events`. `GET /analyses/{id}/events` — события `progress` с `{status, done, total, error}`: первое — снимок (статус из БД, счётчики из Redis; подписка раньше снимка, поэтому событие может прийти дважды), поток закрывается после done / failed; если событий нет 5 с, статус перепроверяется в БД. Keepalive — встроенный в FastAPI (`fastapi.sse`, раз в 15 с). Для полинга `GET /analyses/{id}` отдаёт `progress`.
- **Список партий (сессия 5)**: курсор по `(played_at DESC NULLS LAST, id DESC)` — партии без даты в конце; фильтр `source`; у каждой партии — сводка последнего анализа (статус, точность). `GET /games/{id}` — последний анализ с ходами, если он готов.
- **Импорт Lichess / Chess.com (сессия 6)**: импорт — фоновая ARQ-задача `import_games` (`app/workers/imports.py`), состояние — в таблице `import_jobs` (status, fetched / imported / skipped, error). `POST /imports/lichess {username, max=100 (≤1000)}` и `POST /imports/chesscom {username, months=3 (≤24)}` отвечают 202 с `{job_id, status, imported, …}` (`imported` = 0, пока задача в очереди); прогресс — полингом `GET /imports/{job_id}`. Пока импорт того же ника (без учёта регистра) с той же площадки в queued / running — возвращается он (200), блокировка — строка пользователя `FOR UPDATE`. Каждая страница источника — отдельная транзакция со счётчиками; ошибка источника → failed с понятным текстом («Пользователь X не найден на Lichess»), уже сохранённые страницы остаются.
  - `external_id`: Lichess — id партии; Chess.com — `live/<id>` / `daily/<id>` из URL партии (у live и daily разные счётчики), иначе `uuid`. Дедупликация — тот же unique-ключ, что у PGN; `imported` — только новые (`INSERT … ON CONFLICT DO NOTHING RETURNING`).
  - Цвет пользователя — по нику, **с которого импортируем** (не по профилю). Первый импорт с площадки записывает ник в `users.lichess_username` / `chesscom_username`, если там пусто (по нему ищется цвет во вставленных PGN); заданный ник не перезаписывается.
  - Lichess: `GET /api/games/user/{name}` NDJSON (`pgnInJson`, `clocks`), только классические шахматы через `perfType` (варианты не съедают `max`). Страницы по 100 через `until`; `until` у Lichess исключающий, поэтому следующая страница — с `until = oldest + 1` и `max` больше на число партий с этим временем, повторы отсекаются по id (иначе партии с одинаковым `createdAt` на стыке терялись бы). Необязательный `LICHESS_TOKEN` ускоряет выгрузку (30 партий/с вместо 20).
  - Chess.com: `months` — календарные месяцы, считая текущий; архивы новые → старые, ник в URL в нижнем регистре, URL месяца строится из `CHESSCOM_API_URL`, а не берётся из ответа. Варианты (`rules != chess`) — в `skipped`.
  - HTTP (`app/importers/http.py`): свой User-Agent (`IMPORT_USER_AGENT`), повторы 429 (Retry-After, иначе 60 с), 5xx и сетевых ошибок (1, 2, 4… с), `IMPORT_MAX_ATTEMPTS` попыток; 404 / 410 → «не найден».
- **Объяснения (сессия 7)**: факты (`explain/facts.py`) строятся из сохранённой строки `moves` (оценки, линии, мотивы) — движок не вызывается. Оценки в фактах — за сделавшего ход (`+1.20`, `#3`, `-#2`, `#` — поставил мат). «Лучше было» и упущенные мотивы — только у ошибок и miss: у brilliant / great с Δ ≤ 2 лучший ход формально другой, но подсказывать его неверно. Опровержение и `material_swing` (материал игрока после хода и 4 полуходов ответа, в пешках) — только у inaccuracy / mistake / blunder.
  - Проверка SAN (`explain/validate.py`): каждый токен английского SAN в ответе должен быть среди строк фактов (без учёта `+#` и `0-0`/`O-O`); голое поле (`e4`) допустимо, если поле есть в фактах; обозначение цели «Kg8» допустимо; русская нотация (`Кf3`) — всегда ошибка. Ответ с лишними ходами → один повтор с перечнем лишних ходов → шаблон.
  - Кэш `explanations`: ключ — sha256 фактов с солью `PROMPT_VERSION:kind:provider:model` + язык. Пишутся ответы LLM и шаблон после провала проверки (чтобы не платить за ту же галлюцинацию); шаблон при ошибке провайдера (сеть, лимиты) не кэшируется; при `LLM_PROVIDER=none` в кэш ничего не пишется (шаблоны мгновенные).
  - Провайдеры — через официальные SDK (`google-genai`, `openai`, `anthropic`), модели по умолчанию (переопределяются `LLM_MODEL`): Gemini `gemini-3.1-flash-lite` (самая дешёвая модель текущего поколения; `gemini-2.5-flash-lite` дешевле, но прошлого поколения), OpenAI `gpt-5-nano` (`reasoning.effort=minimal`), Anthropic `claude-haiku-5-5` (`effort=low`). Ключ не задан при выбранном провайдере → API не стартует (ошибка конфигурации, а не тихие шаблоны).
  - API: `POST /moves/{id}/explain {lang?}`, пакет `POST /analyses/{id}/explanations {lang?}` (все объясняемые ходы, к LLM не больше `LLM_MAX_CONCURRENCY` запросов сразу), `GET /analyses/{id}/summary?lang=` (3–5 пунктов, строки «- …»; для неготового анализа — 409). Язык по умолчанию — `users.lang`. Необъясняемые ходы (book, best, …) получают короткий шаблон.
  - Общий разбор (§6.3): точность и фазы игроков, счётчики ошибок, ключевые моменты — до 3 ошибок с падением win% ≥ 10 (падение у лучшего хода — артефакт глубины, не перелом), типичные мотивы наказаний; если `user_color` известен — пишется для этого игрока.

  - Экран разбора: плашки игроков над и под доской, eval-бар слева. Панель справа — два режима: «обзор» (итог в облачке, свёрнутый до 2 пунктов, точность, таблица «белые | значок | чёрные» по классам, фазы со значком по точности — `phaseClass`, пороги на глаз, кнопка «Начать разбор») и «разбор по ходам» (ход с объяснением в облачке, компактный график, список ходов, навигация внизу). Список ходов — фигурная нотация картинками фигур доски (`defaultPieces` react-chessboard; юникод-фигурки зависят от шрифта системы), значимые ходы (brilliant, great, inaccuracy, mistake, miss, blunder) — со значком и цветом класса.
  - Десктоп: панель высотой с блок доски, но не ниже экрана (`h-0` + `min-h-[max(100%,100dvh-2rem)]`), список ходов не меньше 13rem, верх панели прокручивается сам. Телефон: блок доски липнет под шапкой, главная кнопка и навигация — к низу экрана, последние партии на главной — лентой с прокруткой вбок.

## Заметки по окружению

- Запуск: `cp .env.example .env && make up`. Порты на хосте настраиваются в `.env` (`API_PORT`, `WEB_PORT`, `POSTGRES_PORT`, `REDIS_PORT`).
- Проверки: `make test` (линтеры + pytest локально, поднимает postgres/redis), `make test-docker` (pytest в образе backend, где установлен Stockfish).
- Stockfish в образе — официальный бинарник `sf_19` (amd64/arm64), версия задаётся `STOCKFISH_VERSION` в `backend/Dockerfile`. Локально — `brew install stockfish`, иначе тесты движка пропускаются (в Docker — падают).
- Тестовая БД — `chess_review_test`, пересоздаётся на каждый прогон тестов.
- CLI: `cd backend && uv run python -m app.cli analyze game.pgn [--depth N] [--multipv N] [--pool N] [--game K]`.
- **Lichess API**: на дефолтные User-Agent библиотек (`curl/…`, `python-httpx/…`, `python-requests/…`) Lichess отвечает 404 HTML-страницей — отсюда ложный вывод «нужен токен» перед сессией 6. С собственным UA `GET /api/games/user/{name}` работает анонимно. `/@/{user}/download` по-прежнему редиректит на логин (не используем). Проверка руками: `curl -A "ChessReview/0.1" "https://lichess.org/api/games/user/thibault?max=1"`.
- Тесты импорта: клиенты и задача — на фейковых Lichess / Chess.com (`tests/import_fakes.py`, `httpx.MockTransport`); в ctx задачи — `http`. Живые тесты против настоящих API: `NETWORK_TESTS=1 uv run pytest tests/test_import_live.py` (по умолчанию пропускаются). Сквозной импорт через Docker: 40 партий Lichess — 5 с, 2 месяца Chess.com (21 партия) — 3 с.
- База дебютов: `cd backend && uv run python scripts/build_openings.py [--ref <commit>]` пересобирает `app/review/data/openings.tsv` (по умолчанию — закреплённый коммит `lichess-org/chess-openings`, CC0).
- `tests/test_classify_known.py` — 15 ходов из известных партий на настоящем Stockfish (depth 16, свежий однопоточный процесс на ход — детерминированно), ≈ 25 с. Классы на depth 18 те же. Отладка классов на целой партии — колонка «Класс» в CLI.
- Мотивы в CLI — колонка «Мотивы»: мотивы хода, «упущено» (PV1, если сыгран не лучший ход) и «наказание» (ответ соперника, только у неточностей и ошибок). `detect_all` ≈ 3 мс на ход.
- Эталон точности: `backend/tests/data/lichess_accuracy.json` — 46 партий Lichess с их оценками и точностью (разные окончания: мат белых/чёрных, с последней оценкой и без, сдача, время, ничья, пат).
- Анализ через API вручную: `POST /api/v1/games/pgn` → `POST /api/v1/games/{id}/analyze` → `curl -N localhost:$API_PORT/api/v1/analyses/{id}/events`. Замер (сессия 5, Docker на Apple M1): партия 42 хода, depth 18, пул 4 — импорт → SSE → done за 46 с; точность 88.7 / 94.7 против 89 / 95 у Lichess.
- Тесты API и воркера (`test_api_*.py`) идут на фейковом движке (`tests/test_analyzer.FakeEngine`), сквозной — на Stockfish depth 8. Фикстуры: `db` (чистит `games` и `position_evals`), `redis` (очищает тестовую базу Redis 15). Задача воркера вызывается напрямую с контекстом `{settings, db, redis, engine, engine_version}`.
- Объяснения: тесты — на настоящем разборе Оперной партии (`tests/data/opera_review.json`: строки `moves`, Stockfish 19, depth 14; `tests/explain_data.py`), LLM — фейк по сценарию (`tests/test_explain_service.FakeLLM`), провайдеры — с подменой методов SDK. Ключей LLM в `.env` на момент сессии 7 нет: живой вызов провайдеров не проверялся, шаблонный режим проверен сквозным прогоном через Docker. Ручная проверка: `GET /api/v1/analyses/{id}/summary`, `POST /api/v1/analyses/{id}/explanations`.
- Покрытие: в `pyproject.toml` `concurrency = ["thread", "greenlet"]` — без этого coverage теряет строки после `await` в SQLAlchemy async.
- Web в Docker — dev-сервер с hot reload, `NEXT_PUBLIC_API_URL = http://localhost:$API_PORT`. `node_modules` лежит в анонимном томе: после изменения `package.json` — `docker compose up -d --build -V web`. Если меняешь `WEB_PORT`, добавь новый origin в `CORS_ORIGINS`.
- Web локально вне Docker: `cd web && NEXT_PUBLIC_API_URL=http://localhost:8001 npm run dev` (без переменной — `http://localhost:8000`). Сборка: `npm run build` (`/games` и `/games/[id]` — частичный пререндер). Dev-режим в первые секунды медленный (≈ 3 с до гидратации и первого запроса к API), в prod-сборке запрос к API уходит через ≈ 0,3 с.
- Тема Chess.com локально (`web/public/chesscom/`, вне git). Сейчас там: фигуры `neo_wood` 300 px (`pieces/{wk…bp}.png`) и доска `board.png` 1200 px — из скриншота пользователя, обрезана по краю, нарисованные на ней координаты затёрты текстурой той же клетки (приложение рисует свои, и они верны при перевороте доски). Как получить заново: curl / скрипт упираются в проверку Cloudflare, но из обычной вкладки браузера CDN отдаёт картинки с CORS — `fetch("https://images.chesscomfiles.com/chess-themes/pieces/neo_wood/300/wk.png")` со страницы на localhost работает; иначе открыть ссылки и сохранить вручную. Подхватываются после перезагрузки страницы, без перезапуска.
- Turbopack в Docker-контейнере иногда не замечает изменение `globals.css` (bind-mount; не помогает даже рестарт — CSS берётся из кэша в томе `.next`). Лечится: `docker compose exec web sh -c 'rm -rf /app/.next/*' && docker compose restart web`.
- `npm audit` ругается на `braces` через `eslint-config-next` (только dev); `npm audit fix --force` откатывает `eslint-config-next` до 14 — не делать.
- Проверено вживую (сессия 8, Docker): вставка PGN «Партии века» → редирект на разбор → SSE-прогресс (82 позиции) → разбор без перезагрузки (17… Be6 — brilliant, стрелки 18. Bxb6 / Qxc3); импорт 20 партий Lichess (thibault) → список → «Запустить анализ» → разбор; клавиши, клик по графику, линия, «Повтори лучший ход» кликами; ширина 375 px без горизонтального скролла; светлая и тёмная темы.
